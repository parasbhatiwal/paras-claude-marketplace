# Triage

Adapted from Matt Pocock's `triage` skill (MIT; see `THIRD_PARTY_NOTICES.md`).

Moves issues through the state machine in
`../../references/workflow-labels.md`. A PR is an issue with attached code:
same roles, with deltas noted. Every comment posted starts with
`> *Generated by AI via the team workflow.*`

**Not for tickets that `spec-and-tickets` produced** — those were specified in
a grill and are handled by `handoff-gate`. Triage is for what arrives raw.

## Invocation

The maintainer describes what they want; interpret and act. Examples: "what
needs my attention", "look at #42", "move #42 to ready-for-agent", "what is
ready for agents".

## Show what needs attention

Three buckets, oldest first, with counts and a one-line summary each:

1. **Unlabeled** — never triaged.
2. **`needs-triage`** — in progress.
3. **`needs-info` with reporter activity since the last triage notes** —
   needs re-evaluation.

Discovery covers **external** PRs only (not collaborators' in-flight work); an
explicitly named PR is always triaged. Tag each line `[PR]` / `[issue]`.

## Triage one issue or PR

1. **Gather context.** Read everything (body, comments, labels, author,
   dates; for a PR, the diff). Parse prior triage notes so resolved questions
   are not re-asked. Explore the codebase with `GLOSSARY.md` and `docs/adr/`.
   Run two checks: **redundancy** (does it already exist? search by domain
   terms and behavior) and **prior rejection** (`.out-of-scope/`, see below).
2. **Recommend.** State your category + state recommendation, with a short
   codebase summary (including "already implemented"). Wait for direction.
3. **Verify the claim before any grilling.** Bug: reproduce from the
   reporter's steps (use `diagnose`). PR: check it out and run the relevant
   tests. Report: confirmed (with code path), failed, or insufficient detail
   (a strong `needs-info` signal). A confirmed verification makes the brief
   far stronger.
4. **Grill if it needs fleshing out** — run the `grill` skill. For work that
   will become several tickets, continue into `spec-and-tickets` and
   `handoff-gate` rather than hand-writing a brief here.
5. **Apply the outcome:**
   - `ready-for-agent` → brief per `../../references/agent-brief.md`
   - `ready-for-human` → same, plus why it cannot be delegated
   - `needs-info` → triage notes (below)
   - `wontfix` → close with a comment that depends on why:
     already implemented → point to where it lives, no `.out-of-scope/` entry;
     rejected bug → polite explanation; rejected enhancement → write
     `.out-of-scope/<concept>.md` (below), link it, close.
   - `needs-triage` → apply the role; optional comment on partial progress.

One category + one state per issue. If states conflict, flag it and ask
before doing anything else.

## Quick override

"Move #42 to ready-for-agent" → trust the maintainer, confirm what you will do
(labels, comment, close), then act. Skip grilling, but ask whether they want a
brief written — never apply `ready-for-agent` without one.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**
- ...

**What we still need from you (@reporter):**
- <specific, actionable question — never "please provide more info">
```

Capture everything resolved during grilling under "established so far".

## Resuming

If prior triage notes exist, read them, check whether outstanding questions
were answered, present the updated picture, then continue. Never re-ask a
resolved question.

## `.out-of-scope/` knowledge base

Rejected **enhancements** (not bugs) are recorded one file per **concept**,
not per issue, in `.out-of-scope/<concept>.md`: a short design-document-style
note — `# Concept`, the decision, **why** (what would have to change in the
architecture, why it conflicts with the project's focus), and a **Prior
requests** list linking every issue that asked. If a file already exists for
the concept, append the new issue to it. Read this directory early in every
triage and surface matches ("this was rejected in #12 — here is why").
